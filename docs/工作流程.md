# 工作流程与故障处理

## 分工

Trae 是创作者与审稿者，负责读文件、作出创作决定并生成正文。`novel.py` 是本地流程工具，负责检查材料、派发下一步、记录已提交版本和合稿，不调用模型 API。

因此，一次 `python novel.py next` 只返回待办任务。让 Trae 按 `START.md` 连续执行，才构成自动写作流程。普通剧情选择不需要人工，但产品运行边界仍然存在。

## 唯一配置与事实来源

| 内容 | 来源 |
| --- | --- |
| 目标字数、章数、最低章长度、修订上限 | `book.json` |
| 用户叙事要求 | `创作任务书.md` 与用户后续明确要求 |
| 世界观、人物动机和结局约束 | `plans/story-bible.md`、`plans/ending.md` |
| 尚未发生的剧情 | `plans/outline.json` |
| 已发生的事情 | `chapters/` 中最终正文 |
| 事实与人物检索索引 | `memory/`，每条应有原文依据 |
| 已提交的版本 | `state/` 中的工具记录 |

大纲不等于事实，摘要也不能覆盖正文。人物知识与事件时间发生冲突时，先定位原文；确认是正文错误后才修订正文并同步依赖记录。

## 正常流程

1. **初始化**：创建工作目录和进度，不覆盖现有内容。
2. **规划**：先设结局，再编排章节，登记计划。
3. **写正文**：每章按照场景目标、阻力、选择和变化结果推进。
4. **审稿**：取得实际正文快照，记录检查项、问题与证据。
5. **有限修订**：按配置上限处理问题；重大未解决问题阻止提交。
6. **更新记忆**：从最终正文抽取摘要、事实、人物变化、伏笔及原文证据。
7. **提交**：检查正文、审稿和记忆一致后登记本章，继续下一章。
8. **全书检查**：章节全部完成后，检查结局、人物弧线和伏笔，并核对实际长度。
9. **导出**：按数字章序合并 Markdown 和纯文本，保存验收报告。

章节快照包含两个哈希：`manuscript_sha256` 绑定本章正文，`context_sha256` 绑定本章计划、全局约束和已提交前文／记忆。审稿与记忆都必须匹配这两个值。

正文没有变化，也可能因前文或设定改变而失去有效审稿。不要直接复制新哈希来“修好”记录：必须先重新检查变化的影响，再更新审稿与事实记录。

## 如何省上下文与额度

- 每章读取相关设定、本章计划、相邻正文和必要事实记录；涉及久远伏笔时再回读对应原文。
- 不在每次请求里重复装入整本小说，也不依赖不断压缩的单份摘要作为全部记忆。
- 以固定模型完成主要写作，有明确质量原因时再调整；更换模型后重新校准叙事风格。
- 限制润色轮数，避免无限自我推翻。新问题需要有具体证据。
- 多 Agent 可以分担检查，但连续剧情的正文保持顺序生成，由一个主创提交。

这些措施减少重复工作，不能保证某个固定字数只消耗多少额度。策划、回读、审稿和修订也会计费。

## 常见情况

### 首次运行报 Python 找不到

Windows 检查 `python --version`，macOS/Linux 检查 `python3 --version`。需要 Python 3.10+；本项目不用安装第三方 Python 包。解释器缺失是环境问题，先处理环境，再执行初始化。

### Agent 只给大纲就结束

确认使用能读写文件和执行命令的 Agent，并明确发送“读取 START.md，按 next 的任务持续执行直到全书验收与导出完成”。确认项目规则已加载。不要把大纲完成当作全书完成。

### 下一步返回未完成草稿

保留已有正文，读取结尾和本章计划，从未完成场景继续。正文完成后才审稿、更新记忆和提交。

### 审稿或记忆哈希不匹配

1. 执行 `python novel.py snapshot --chapter N` 获取当前 `manuscript_sha256` 与 `context_sha256`。
2. 检查本章、前文或全局设定发生了什么变化；必要时对照备份。
3. 结合最新前文和设定重新审稿，并重新核对记忆中的原文证据。
4. 更新两个哈希及检查记录后执行 `check --chapter N`，通过再 `commit --chapter N`。

不要随手把哈希改成一致来掩盖陈旧审稿。对于已提交的章节，使用下一节的正式重审流程。

### 已提交章节需要修改

```bash
python novel.py reopen --chapter 12 --reason "第12章的时间线与第15章冲突，需要修订并复核后续影响"
```

该操作备份并撤销从指定章开始的已有提交登记，移除这些章的旧审稿和记忆文件，仅保留正文。归档内容在 `revisions/` 中。它不会要求你重新写所有后续正文：保留仍然正确的内容，逐章复核影响、重新生成审稿和记忆，然后按序提交。

不要直接修改 `state/` 中的哈希或已完成章数。否则无法可靠区分真正完成、漏写和被修改的章节。

如果 `reopen` 在归档审稿后意外中断，进度可能暂时指向已移入备份的文件。先确认上次命令已退出；如存在遗留 `state/workflow.lock`，核实没有其他写作命令运行后再移除。然后对同一章重新执行 `reopen`，完成失效处理。原始内容可以在 `revisions/` 中找回，不能通过删除进度解决。

### 计划登记后又修改了设定或配置

先确认修改符合用户要求，并区分变更范围：

- 尚未提交章节的 `outline.json` 条目变化：使用 `accept-plan --reason "具体修改原因"` 重新登记。
- 已提交章节的大纲变化：先从受影响章节 `reopen`，再重新登记并复核。
- 已经有提交章节，且修改 `book.json`、`创作任务书.md`、`plans/story-bible.md` 或 `plans/ending.md`：这些是全局约束，必须先 `reopen --chapter 1 --reason "变更与复核计划"`，再 `accept-plan --reason "具体修改原因"`，按顺序复核与提交。

因此，书名等已确定参数应在第一次 `accept-plan` 前填好。不要通过重建进度抹去既有校验。

### 全书长度不符合目标

检查是否缺少实际剧情，或存在冗余。按故事需要补写、删减与重审相关章节，不用大段重复内容凑长度。目标本身确实需要调整时，应在唯一配置 `book.json` 中明确修改，记录原因并重新登记、验收。

### Trae 停止响应、额度耗尽或要求权限

保留当前文件，处理真实阻塞后输入“继续写书”。不要删除项目重新开始，也不要期待本工具能代替 Trae 绕过产品限制。

### 工具返回 `action=blocked`

停止写后续章节，读取 `problems` 或 `error`，保存具体问题并排查。明确的格式错误可修正后重试；达到修订上限仍有重大问题，或运行资源／权限不足时，应停止并说明恢复条件。不要反复刷同一条 `next`、重置修订计数或改状态来跳过阻塞。

### 最终导出失败

先执行 `check` 和 `next`。常见原因是缺章、已提交内容变动、长度不符、最终审稿尚未完成或绑定了旧快照。解决具体问题后再次导出。

## 完成意味着什么

工具层面的完成包括：章节齐全、顺序正确、长度符合配置、版本记录一致、提交与最终审稿符合约定、导出文件实际存在。

AI 语义审稿包括：因果成立、人物知识合理、主线收束、伏笔兑现、风格和重复问题已检查。这些判断仍可能出错；验收报告不是出版质量保证，也不替代你最终决定是否发表。
